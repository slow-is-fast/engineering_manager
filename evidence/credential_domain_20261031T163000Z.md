# §10.29 一条没人测过的放行路径：`verify_credential_domain`

- 日期：2026-10-31
- 起因：本地跑 `gov_run.py --all` 时 `T-VD-01b` 判红（个人 PAT 能写控制面）
- 结果：脚本改为**不可判定即拒绝**；补 T-CD-01..05 五条用例；6 处变异全捕获
- 诚实代价：本地 `gov_run --all` 在这一步**必然**红。这是事实，不是缺陷

## §10.29.1 起因：一个"红"引出的另一件事

本地跑 `--all` 时 `verify_credential_domain.py --expect-deny` 判红：

```
FAIL(T-VD-01b): data-plane credential WROTE to control plane! 凭证域被破坏
```

第一反应是"环境问题"——本地 `GH_TOKEN` 是个人 PAT，横跨两域；CI 的 `GITHUB_TOKEN`
按仓库作用域，写控制面会被 403 拒。所以 CI 绿、本地红，看起来天经地义。

但去读代码时发现一件更糟的事。

## §10.29.2 真正的缺陷：一条默认开启的放行路径

脚本原来有两种模式：

| 模式 | 凭证可写控制面时 | 退出码 |
|---|---|---|
| `--expect-deny` | 判"凭证域被破坏"，失败关闭 | 1 |
| 无参数（自称"审计模式"） | 打印 `INFO ... 人类 Owner 横跨两域属预期` | **0** |

也就是说：**只要不传 `--expect-deny`，跨平面凭证就自动变绿**。而它为自己写的理由
是"人类 Owner 横跨两域属预期"——听起来合理，但这条理由偷换了对象：本检查要验的
是「**数据面运行时凭证**不得写控制面」，本地 PAT 能写控制面这件事，证明不了任何
关于数据面凭证的结论。测不到要测的东西，正确结论是"**无法判定**"，不是"属预期"。

更关键的是：**这个脚本此前一条单元测试都没有**，只在 CI 里被引用一次。一条没人测
过的放行路径，等于一个默认开启的开关——它不会在任何评审里被看见，因为评审看的是
"这个检查存在且 CI 通过"。

## §10.29.3 改成什么

```
能写控制面吗？
├─ 不能            → PASS（唯一能证明分域有效的读数）
└─ 能 → 清理痕迹 → 在哪跑？
        ├─ CI 环境（GITHUB_ACTIONS / CI）→ 凭证域被破坏，失败关闭，阻止合并
        └─ 非 CI                          → 无法判定，同样失败关闭
```

三处刻意做硬的地方：

1. **"无法判定" ≠ "通过"**。不可判定即拒绝，这是本规范一贯的取向。把它写成
   "属预期"就等于宣布"本地跨平面凭证没问题"——而恰恰是这种凭证绝不能交给 Agent。
2. **`--expect-deny` 不再是档位开关**。参数不传也能得到相同的失败结论，只是诊断
   文案不同。参数能改判定结果，就有人会少传一个参数。
3. **环境判定读平台注入的环境变量**（`GITHUB_ACTIONS` / `CI`），不是"我觉得我在 CI"。

## §10.29.4 代价要写清楚

本地 `gov_run.py --all` 现在在这一步必然红。这不是回归，是**事实浮出水面**：
本地凭证不足以完成这项判定。以前它也是红的（"凭证域被破坏"），只是诊断说错了
对象——把"人拿着 PAT 在跑"说成了"凭证域配置坏了"。现在说的是真话。

想让本地跑通只有两条路，都不该靠改检查实现：

1. 换一个仅数据面作用域的 token；
2. 在 CI 里跑（那里才是这项判定的有效环境）。

## §10.29.5 用例与变异

新增 `tests/test_credential_domain.py`（T-CD-01..05），全部用 mock，不碰真实仓库：

| 用例 | 钉住什么 |
|---|---|
| T-CD-01 | 被拒 = 通过（唯一的有效读数） |
| T-CD-02 | CI 里能写 = 凭证域被破坏，不是"环境差异" |
| T-CD-03 | **核心**：非 CI 下能写 = 无法判定，不是"属预期" |
| T-CD-04 | `--expect-deny` 与否不改变"能写就失败"的结论 |
| T-CD-05 | 环境判定读环境变量，不是猜 |

变异 6 处 / 6 处捕获 / 0 逃逸：恢复放行路径（M01）、不清理痕迹（M02）、
`in_ci` 恒为假（M03）、`allowed` 恒为假（M04）、把 `sys.exit` 换成 `print` + `return 0`
（M05，看着报错其实放行）、环境判定放宽（M06）。

**过程中踩的一次坑**：M01/M05 第一次注入后，全套件报的是模块级
`unittest.loader._FailedTest`——那是**语法错误导致的收集失败，不是真捕获**。
按老规矩重做成行级替换（语法 OK）后，归因才落到具体用例。
"红了"和"被正确的用例抓住"是两回事，这一点是第二次栽，值得记住。

## §10.29.6 由此引出的一条建议

`verify_credential_domain.py` 不是特例。本轮只对它做了"有没有放行路径"的体检，
其余 12 项必需检查同样值得过一遍——**"检查存在"和"检查在每种情形下都会拦"是两件事**。
这也写进了 §11 报告的下一步第 3 项。
