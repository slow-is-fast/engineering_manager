## §10.26.1 AUD-015-03：四类隔离演练编排器

新增 `executor/drill.py`。与 `incident.py` 的分界：

| | 管什么 | 回答的问题 |
|---|---|---|
| INC-01（`incident.py`） | 隔离这个**动作**：要证据保全、清单非空、关闭须通知/复验/复盘齐备 | 这次处置做得对不对 |
| DRL-01（`drill.py`） | 四类场景是否**练过**、每步有没有证据、复盘有没有结论、记录有没有过期 | 真出事时我们练过吗 |

只测 INC-01 的字段校验，证明的是"处置记录填得规范"；它不能证明四类场景都
演练过。一次都没练过的流程，真出事时等于没有流程——而这类缺口平时完全
不可见，因为没有任何检查点会触发它。

几处刻意做狠的地方：

1. **每一步都要证据**。空证据 = 只声称做过。处置记录里最不值钱的就是"我做了"。
2. **恢复必须被复验过**，不是"我恢复了"。声称恢复而没复验是自欺：看起来
   处置完了，实际留了一半。
3. **复盘必须有结论与待办**。复盘没结论等于没复盘，"已复盘"三个字不算。
4. **四类缺一不可**。缺一类的报告不能算"演练完成"。
5. **记录 90 天过期**。练过一次不等于永远练过。
6. **同一场景不许覆盖**。否则"再跑一次并覆盖"就能把失败的那次抹掉。
7. **`env` 只能是 `simulated`**（见 §10.26.3）。

## §10.26.2 AUD-013-03：新增 `excepted` 档

这条断言受 EXC-01 约束：第二人类主体不可达（已实证——第二 PAT 不构成独立
审批主体，GitHub 按主体而非凭证判定独立性）。机器侧能做的补偿
（`scripts/verify_reviewer_credential.py --expect-deny`）同样受同一例外约束：
它需人工注入 reviewer token，CI 里的 `GITHUB_TOKEN` 不是 reviewer 凭证，
拿它测会变成另一件事（测的是"工作流 token 不能写"，不是"评审凭证不能写"）。

此前记为 `unimplemented`，与"忘了做"混在同一个桶里。新增 `excepted` 档把它
单独标出来，语义是：**已知做不到，且已登记风险**。

### 关键设计：excepted 不填平任何东西

| 口径 | 取值 |
|---|---|
| 计入 `satisfied` | **否** |
| `machine_complete` | **False** |
| 阻止"声明已关闭" | **是**（仍是 `closure_without_acceptance` 的阻断项） |
| 引用无效例外时 | `excepted_without_valid_exception`，连"登记例外"都算不上 |

例外是"把洞标记出来"，不是"把洞填平"。一旦把它当 `ok=True`，`excepted` 就
变成"改一个字段就能让未满足的断言消失"的后门——比 `unimplemented` 更危险，
因为它看起来像被处理过了。这条由 2 条用例钉住，并由 3 个变异验证：
把 `ok` 改成 `True`、把 `excepted` 从类型白名单移除、把"例外一律采信"，
三者的变异全部被捕获。

例外引用必须有效：`exception_ref` 指向的例外须满足 `exception_valid`
（ACTIVE + 人类批准人 + 未过期 + 有补偿控制 + 有撤销条件 + 有 waives 目标）。

## §10.26.3 诚实边界

**一、编排的是受控模拟演练。** `env` 只能声明 `simulated`，声称 `production`
一律拒绝。把模拟说成生产演练，比不演练更糟——它会让"我们演练过"这句话
失去意义。真实生产隔离实操需要真实环境、真实凭证隔离与独立值守，不在本模块
范围内（`AUD-015-04`，manual）。`T-DRL-15` 把"模拟演练证明不了生产可用性"
固化成用例，而不是写在注释里。

**二、`excepted` 不能降低门槛。** 它不改变任何计数口径：仍计入未满足、
仍禁止 `machine_complete`、仍阻止声明关闭。AUD-013 因此仍是"未闭合"。

**三、附带发现：EXC-01 的到期日两处不一致。**
`governance/exception_register.json` 写 `expires: 2027-01-31`，而
`governance/quality_baseline.json` 的 `exceptions` 里写 `expires: 2027-04-30`。
前者自己声明"不一致时以本文件为准，并视为登记缺陷（REG-01 类）"。本轮
**未修**——改到期日属于例外登记变更，需要 Owner 决策（是补到 2027-04-30
有依据，还是基线抄错了）。记录在此，因为 `excepted` 的判定依赖
`exception_valid` 的未过期检查，两个日期差三个月会影响什么时候突然变红。

## §10.26.5 一处过程教训

替换 `executor_pin.json` 的 `bump_reason` 时只换了字符串**前缀**，旧文本
后半段残留在同一行，把 JSON 改坏了（加载直接抛错）。教训：替换长字符串字段
时要整段替换，或改完立刻 `json.load` 验证一次。已修，未影响任何已提交内容。
