# 冷读复核：三条刚转 automated 的控制，被查出"看起来在检查"（2026-10-30T21:50+08:00）

**CI 追溯**：演练 run `41065699717`（**失败**，证明 T-QA-04 真的会红）→ 修复 run `41066075739`（成功：132 tests / T-QA-01/02/04 全 PASS / G1 阻断 10 / 断言 63）。

---

## 一、为什么要做冷读

上一轮我把三条控制从 `drill` 升成 `automated`，写了 6 条负向用例，变异检验 5 条全红 —— 看起来很完整。但**我既是实现者又是审查者**，这本身就是覆盖错觉的来源：我知道每个分支想干什么，就会不自觉地按"它应该对的"去构造用例。

所以这一轮把三个脚本交给一个**没有本轮上下文**的视角重读，并且要求它实测而非只读代码。

结果：三条控制**都有**真实缺陷，其中一条是致命的。

## 二、F1：T-QA-04 在 CI 上是恒绿装饰（最致命）

漂移检测依赖比较两个提交：

```
B = 基线文件最后修改的提交
G = 治理范围最后修改的提交
B 严格早于 G → 失败
```

而 GitHub Actions 的 `actions/checkout` **默认 `depth=1`**。浅克隆里只有一个提交，两个查询都返回 HEAD，于是 `B == G`，脚本打印：

```
PASS(T-QA-04): baseline reviewed together with governance @051eb29f2f8f
```

**它在没有任何历史可比的情况下，输出了一条正向保证。**

我亲自复现（不依赖代理的结论）：

| 场景 | 结果 |
|---|---|
| 全历史仓库，只改 `scripts/`、不动基线 | `FAIL ... baseline drifted` ✅ 正确 |
| 浅克隆（`--depth=1`），同样的改动 | `PASS ... reviewed together` ❌ 恒绿 |

危害不只是"没拦住"，而是**它撒谎了**——宣称"基线与治理同批审查"，实际无从判断。而我上一轮把这条 `PASS` 写进了证据文件当通过依据。

**修复**：`checkout` 加 `fetch-depth: 0`；脚本对 shallow 仓库**失败关闭**（不可判定即拒绝），不走 `==` 短路。

**实证（不是靠推理）**：推一个只改治理文件、不动基线的提交 → CI **真的红了**：

```
FAIL(T-QA-04): baseline drifted — governance changed in ea619bc843c8
               but baseline last reviewed in df4e05fbb371
失败步骤：T-QA-04 quality baseline complete and not drifted
```

再按正规路径同批更新基线 → 绿。**门禁从"装饰"变成了真会响的警报。**

## 三、其余修复

| 编号 | 缺陷 | 修复 |
|---|---|---|
| F2 | 只看"是否同批改动"，不看改了什么。一个提交里把 `min_test_count` 110→1、`required_checks` 清空，顺手更新基线即通过 | 单调性校验：下调阈值 / 移除必需检查 / 扩大例外，必须附 `change_approvals` 审批记录 |
| F2b | 判定锚点 `applies_to_sha` 由基线自己写，想放行就改它 | 锚点改用 git 提交历史（不可伪造）；`applies_to_sha` 降级为纯追溯字段 |
| F10 | 只看提交，工作区改动完全不可见 | 治理范围有未提交改动 → 失败关闭 |
| F3 | 只扫 `*.yml`，改名 `.yaml` 即失明；扫到 0 条也打印 PASS | 两种后缀都扫；**扫到 0 条 = 失败关闭**（"什么都没看见"绝不是通过） |
| F4 | `docker://` 无条件豁免，与浮动 tag 是同一类风险 | 必须 `sha256:` digest pin |
| F5 | 本地 composite action 豁免且不扫定义，里面的 upstream 调用没人管 | 跟踪 `./` 引用的定义文件（可在仓库任意路径）+ 断链检测 |
| F6 | 行正则覆盖不到流映射 / 引号 key / 锚点别名 | 改用 PyYAML 结构化解析；缺失时降级但**明确标注 DEGRADED** |
| F7 | "缺键才算缺"被错误推广：`required_checks: []` 也通过 | 必需检查与可信 CI 来源不得为空，且指向的文件必须真实存在 |
| F8 | `isinstance(True, int)` 为真，阈值 `true` 当下限 1 放行 | 拒绝 bool / 非正数 / 非整数 |
| F9 | 正则计数：`async def` 漏计、三引号里写 `def test_x` 可刷数、子目录不计 | 改用 AST 统计 |
| F11 | GOV_PATHS 含 `tests/`，改个测试也要重批基线 → 审批盖章化 | 去掉 `tests/`（删测试由 T-QA-02 管，不重复记账） |
| F14 | 非字符串值让校验器崩成 traceback，日志无 `T-QA-04` 标记 | `str()` 包裹，统一走 `fail()` |

## 四、变异检验：12 条全红，0 逃逸

但**第一轮跑出 2 条逃逸**，而且两条都是我自己写的用例有问题是假绿：

1. **"移除必需检查"用例**：我用 `required_checks=[]`，结果被"不得为空"先拦下——它测的其实是另一条规则。改成移除**部分**必需检查后，才真正命中目标。
2. **"composite action"用例**：action 放在 `.github/actions/` 下，而 `workflow_files()` 本来就预扫这个目录，所以"禁用跟踪逻辑"不影响结果。改用放在仓库任意路径（`.github/actions/` 之外）的场景，才锁住跟踪逻辑。

**这两条正是我一直抓的那类缺陷，出现在我自己的用例里。** 上一轮那 6 条"样板级"用例给了覆盖错觉；这轮 29 条才真的覆盖到每条路径。

## 五、顺带把测试下限对齐实际值

`min_test_count` 110 → **139**（实际值）。**删除余量归零**——任何一条用例消失都会红。

收紧（上调）不需要审批，放宽（下调）才需要；这条规则由 T-QA-04 强制，并有双向用例验证（无审批→拒、有审批→放行）。

## 六、诚实边界与残留

- **F12 自指问题未解决**：`verify_quality_baseline.py` 自身源码在 `scripts/` 内，而 `scripts/` 属于 GOV_PATHS。所以"改判定逻辑"和"改基线"可以在同一个提交里完成——理论上存在同时放宽规则与满足规则的可能。缓解手段只有流程（改脚本与改基线分开提交），没有技术手段。**这是已知的、未修的缺口。**
- **F13 部分**：YAML 锚点别名现在由 PyYAML 解析后取真实值（已解决）；块标量 `uses: >-` 仍会取出 `>-` 字符串并被拒（失败关闭方向，可接受）。
- **PyYAML 是新增依赖**：CI 里显式 `pip install pyyaml`；若装不上会降级为行正则并标注 DEGRADED——**降级是可见的**，但覆盖确实不如严格模式。
- **冷读本身也可能有盲区**：它是一轮审查，不是证明。判定的锚点（git 历史）比原版（基线自证字段）更难伪造，但"改判定脚本 + 改基线同批提交"仍未被技术性阻断。
- **演练产生了两次 CI**：一次红（受控，证明门禁真响）、一次绿（修复）。红的那次是故意的，与 PR #2/#3/#4 的演练惯例一致——**演练型证据以"被拒"为通过标准**。
