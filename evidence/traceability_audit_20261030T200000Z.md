# 44 条 tested 控制的记账复核（2026-10-30T20:00+08:00）

**CI 追溯**：数据面 run `41001745909`（103 tests OK；`T-CLM-01` 步骤首次在 CI 执行并通过：`PASS(CLM-01): no unbacked absolute claims in 35 docs`；`RESULT: ALL PASSED`；成熟度等级 G1 / 阻断 10；§四 断言 90 条满足 63、全通过问题 1/22）；控制面 run `41001688492`（88 用例 OK）。

**为什么做这件事**：上一轮修双向闭合时揪出两处"引用挂错"（`CTX-02`/`CTX-03` 按编号配对挂反、`REC-01` 用相邻控制凑覆盖）。那两处都是**逐条比对语义**才发现的，校验器一条都没报——它只能查"引用存不存在"，查不出"引用对不对"。所以这一轮把同样的方法用在全量上：44 条声称 `tested` 的控制，逐条核对它的 `test` 字段是不是真的指向一个存在的用例，而那个用例是不是真的在验证这条控制的语义。

---

## 一、复核口径

对每条 `tested` 控制做两问：

1. **`test` 字段指向的东西存在吗？** ——能解析到 `tests/*.py` 的用例方法，或 `.github/workflows/*.yml` 的 CI 步骤。
2. **它验证的是这条控制的语义吗？** ——比对控制的 `evidence` / `failure` 与用例的实际断言。这一问工具答不了，只能逐条读。

---

## 二、结论：41 条 automated + 3 条 drill

| 证据类型 | 条数 | 含义 |
|---|---:|---|
| `automated` | 41 | `test` 可解析到真实用例或 CI 步骤，**每次改动都会再跑一遍** |
| `drill` | 3 | `QA-01`、`QA-02`、`BASE-01`——只有一次性演练记录（PR #3/#2/#4），无常态化自动检查 |

`drill` 不是错误，但必须贴标签：一次性演练被当成常态化保障，是"看起来有覆盖"的另一种形式。这三条的 `integration_evidence_uri` 指向真实存在的演练 PR（已逐个用 `gh pr view` 核实，标题与 `test` 字段一致）。

**语义比对结果**：41 条 automated 中，32 条有 executor 单元用例，**逐条读过后全部吻合**——包括最容易不知不觉漂掉的几条：`MEM-01`（5 个用例分别覆盖来源校验/摘要 stale/来源失效级联/过期/父不可用）、`SMT-01`（6 个）、`AUTH-02`（4 个）、`GATE-01`（12 个）、`CRED-01`（6 个）。另有 9 条依据 CI 脚本或静态用例（`AUD-01`/`REG-01`/`REG-02`/`VD-01`/`RVF-01`/`CLM-01`/`QA-04`/`ID-02` 等）。

## 三、揪出的三处记账不实

### 3.1 `ID-02`（P0）：证据指向的 PR 与控制无关

`integration_evidence_uri` 指向 **PR #5**，`evidence` 写的是"fine-grained token 在数据面可写、对控制面写被 403 拒（PR #5 演练）"。

实际 `gh pr view 5`：标题 **"T-QA-03 演练：Reviewer 独立性"**，正文是"凭证≠主体的实测：本 PR 由 agent token 创建，尝试用 Owner 凭证审批"，改动文件只有一个 `drill_qa03_probe.md`。**里面没有任何 token 写控制面 403 的内容。**

处置：`test` 改为 `T-VD-01b`（CI 里的"凭证域检查：数据面 token 不得写控制面"，这才是对得上语义的真实依据），URI 改为该步骤所在的真实 run，`evidence` 里写明更正过程，并标注**只覆盖了"对控制面写被拒"这半边**，"数据面可写"这半边没有自动化实证。

### 3.2 `QA-04`（P1）：`test` 字段指向不存在的用例

`test` 字段写的是 **`T-QA-05`**——仓库里根本没有这个用例，`grep` 全仓无匹配。而它的 URI 指向 **PR #4**，但 PR #4 的标题是 **"[演练4] T-QA-04 SHA 绑定"**，演练的是"旧 SHA 的绿检不能复用给新提交"——那是 **`BASE-01`**（质量基线 SHA 绑定）的语义，不是 `QA-04`（criterion-to-evidence mapping）。

处置：`test` 改为 `T-CLOSE`（§四 验收矩阵本身就是"验收标准 → 可判定断言"的映射，且 CI 有对应步骤），URI 改为真实 run。同时把这三条 `drill` 型证据标注清楚。

### 3.3 `CLM-01`（P1）：脚本没进任何 CI，URI 指向的执行与它无关

`integration_evidence_uri` 指向**控制面 run `40844523493`**。但控制面仓库**连 `scripts/` 目录都没有**，那个 run 只跑 executor 负向用例；而 `check_claims.py` 实际在数据面 `scripts/` 下，且**当时没有出现在数据面 CI 的任何步骤里**。

也就是说：这条控制声称 `tested`，但它的检查从未在 CI 中被执行过——只在本机手动跑通过。

处置：**把 `T-CLM-01` 步骤加进数据面 `governance.yml`**（这是本轮唯一的实质功能改动），`evidence` 里写明更正；URI 在该步骤真实执行后补记。

## 四、把"能自动查的"变成机器判定

三处缺陷里，`QA-04` 这类（引用指向不存在的用例）**完全可以自动查**。新增两条失败关闭断言（`scripts/validate_controls.py`）：

1. 每条 `tested` 控制必须声明 `evidence_kind`：`automated` 或 `drill`；
2. `automated` 的 `test` 字段必须能解析到 `tests/*.py` 的真实用例或 workflow 的真实步骤；`drill` 的 URI 必须指向 PR。

配套两条负向用例：`T_REG_05_ghost_test_ref`（把 test 改成 `T-GHOST-99` → 必须失败）、`T_REG_06_tested_without_evidence_kind`（去掉声明 → 必须失败）。

**变异检验（3 条全红）**：

| 变异 | 结果 |
|---|---|
| `MEM-01.test` → `T-GHOST-99` | **CAUGHT** `test ref resolves to no real case` |
| `CRED-01` 去掉 `evidence_kind` | **CAUGHT** `tested control without valid evidence_kind` |
| `QA-01` 标 `drill` 但 URI 不是 PR | **CAUGHT** `drill 但 URI 不是 PR` |

还修了一个连带问题：负向用例的"干净副本"原先只拷治理 JSON 和审计清单，不拷 `tests/`、`workflows/`——新断言在副本里会把所有控制判成幽灵用例，**阴性对照失效**（会让 T_REG_04 这类用例假绿）。已在 `make_tmp` 补拷这两处。

## 六、诚实边界

- **本次复核只覆盖 44 条 `tested`**，5 条 `not_enforced`（`REC-04`、`QA-03`、`AUD-02`、`AUD-03`、`RVW-01`）未比对。
- **"语义吻合"是我的判断，不是机器判定。** 41 条 automated 里我只逐条读了有 executor 用例的 32 条；`AUD-01`/`REG-01`/`REG-02`/`VD-01`/`RVF-01`/`CLM-01` 是把 CI 脚本/静态用例的存在性当作吻合依据，脚本内部是否真的覆盖了该控制的全部语义，本轮没有逐行验证。
- **`drill` 型证据（3 条）的"通过"标准是演练被拒或未合并**，与时间无关——它证明门禁当时生效过，不证明今天仍然生效。
- **`ID-02` 仍是半边证据**（只验证了"不能写控制面"）。
- **`verified` 仍为 0**，全部 `tested` 都是逻辑验证，受 `EXC-02`。
- **复核本身没有可机检的完整性保证**：我可能漏读某条用例。能机检的部分（引用可解析性）已经固化进校验器，不能机检的部分（语义是否对得上）下次还得靠人再做一遍。
