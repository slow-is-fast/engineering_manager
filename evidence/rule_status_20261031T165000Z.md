# §10.30 规则层 status 声明为非约束性字段

**日期**：2026-10-31T16:50+08:00
**关联**：`rule-registry.json` 顶层 `rule_status_participation: schema_only` + `rule_status_note`；整体复核报告 §3 第 2 点、§7、§8（原"规则层状态未维护"项）

## 事实（先查证，再定调）

`scripts/validate_controls.py` 第 108 行对规则层 `status` 仅做：

```python
st = r['status']
assert set(st) == set(STATES), f"bad state keys: {r['rule_id']}"
```

即**只校验键集与布尔类型**，从不强制 `documented/configured/tested/verified`
任一为真，也从不把它用于任何门禁判定。真实的执行信号来自：

- `control-catalog.yaml` 各控制的 `state` 块（会被 `validate_controls` 逐条核对）
- `governance/acceptance_matrix.json` 的验收断言

因此"53/59 条规则只标 `documented`"**不是记账缺口，是冗余信号的默认值**——
它既不参与判定，也不反映真实状态。把它当成"缺口"去逐条补齐，等于维护一份
永远滞后于 `control-catalog.state` 的镜像，纯属噪音。

## 处置

在 `rule-registry.json` 顶层新增两段声明，使字段语义显式、不再误导：

- `rule_status_participation: "schema_only"`（机器可读标志）
- `rule_status_note`：说明该字段仅做结构校验、不参与门禁、不得被读作"规则
  是否已落地"的证据；需要规则级执行状态时查其 `enforcement.controls` 指向的
  控制条目。

**未降低任何门槛**：该字段此前就不参与判定，声明只是如实标注一个已存在的
事实，不是把某道闸门改成文档声明。这与"不得用文档声明替代机器判定"的原则
不冲突——被声明的对象本来就不是机器判定。

## 验证

- `validate_controls.py`：通过（`59 rules registered (1 without runtime control)`）
- `check_governance_refs.py`：通过（新顶层键不在 REF_FIELDS，不触发 ID 解析）
- 全套件 256 通过

## 结论

规则层 `status` 由"既不维护也不声明"的悬空状态，变为"显式声明为非约束性"的
诚实状态。报告 §7 / §8 对应项已划掉并指向本证据。
