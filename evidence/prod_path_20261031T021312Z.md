# §10.25 生产路径接入：审计生命周期与数据闸门真的跑在门禁上

- 日期：2026-10-31
- 断言：AUD-014-03（保留策略 / 伪造来源识别 / 恢复）、AUD-016-03（删除后再现 / 超期保留 / 未经批准传输）
- 支撑控制：EVD-01、EVD-02（审计链与不可用失败关闭）、ISO-01（Run 绑定）
- 状态：**operational（仅这两条断言的机器判定部分）**；控制目录里没有专属控制条目，见 §10.25.6 的缺口

## §10.25.1 问题：模块全绿，门禁里没有调用点

`executor/auditlifecycle.py` 与 `executor/datagate.py` 写完后，只有
`tests/test_executor_negative.py` 在调用它们。CI 里十几项检查各跑各的：

- 没有任何东西记录"这次治理跑过了"；
- 没有任何东西检查各项检查**真的都跑了**（把某一步从 workflow 里删掉，
  其余步骤照样全绿）；
- 模块的保留期、来源识别、恢复三条语义，在实际运行中一次也没被执行过。

测试覆盖了逻辑，不等于控制生效。这是本项目最想防的那种自欺，也是
"tested ≠ operational" 的具体形态。

## §10.25.2 接法

新增 `scripts/gov_run.py`，CI 的每一项检查都改为经它执行：

| 模式 | 作用 |
|---|---|
| `--check <path>` | 跑一项 `required_checks` 里的检查，把结果写进带来源声明的审计流 |
| `--verify` | 对整条流验收：链完整性 / 来源可归因 / 保留期 / 本次运行的必需检查是否全部落地 / evidence 台账 |
| `--all` | 本地一把梭（生成 run_id → 全部检查 → 验收） |
| `--accept-evidence` | 登记 `evidence/` 下的证据文件，需 `--by` 与 `--reason` |

审计事件：`gov.check.completed`（来源 `gov-run`）、`gov.trail.verified` /
`gov.trail.finding`（来源 `gov-verify`）、`gov.evidence.registered`
（来源 `gov-evidence`）。来源与保留期不是写在注释里，而是
`governance/audit_policy.json` 的机器可读字段——`ProvenanceRegistry` 和
`RetentionPolicy` 直接照它建。

## §10.25.3 五处刻意的失败关闭

1. **审计流不存在 → 红。** 缺流当"没问题"是最贵的一种假绿。
2. **检查不在 `required_checks` 里 → 拒绝记录。** 能让调用方指定"写什么进
   流"，这条流就不值钱了。
3. **链断了 → 隔离坏段后拒绝追加。** 坏段原样落到
   `evidence/audit/quarantine/`；在坏链上多写一条，等于把问题盖住。
4. **必需检查没有落地事件 → 红。** 不跑就算过，等于门禁可以静默缺席。
5. **没有 run_id → 拒绝判定。** 判不了就说判不了，不要"跳过这项检查"。

## §10.25.4 检查参数从治理配置读，不从 CI 读

原来 CI 里有 `python scripts/verify_evidence_freshness.py --enforce`、
`verify_credential_domain.py --expect-deny`，`check_admission_gate` 与
`check_audit_closure` 还是两步调用（出报告 + 收紧判定）。

如果这些参数由 CI 传，CI 就能悄悄用弱模式（不带 `--enforce`）跑一遍，审计流
里照样记一条 `verdict: ok`——"跑了、也绿了、但不是那个档位"，这种假绿最难发现。

现在 `audit_policy.check_args` 记录每项检查的**完整调用序列**：

```json
"scripts/check_admission_gate.py": [[], ["--require-level", "G1"]],
"scripts/check_audit_closure.py": [["--acceptance"], ["--enforce"]]
```

调用方无权指定参数；事件里也记下 `args` 与 `invocations`，事后可核。

## §10.25.5 evidence/ 改为登记制

`governance/evidence_ledger.json` 记录每个证据文件的 sha256、类别（`evidence`
365 天 / `test-artifact` 90 天）与产生时刻。`--verify` 用 `DataGate` 校验：

- 内容与台账哈希不符 → 红（被悄悄改）
- 台账有、磁盘没有、又无批准记录 → 红（未经批准的删除）
- 批准删除后又出现在磁盘 → 红（删除后再现）
- 磁盘有、台账没有 → 红（未登记的证据，本来就不该被当证据）
- 已批准删除的文件不能靠重新登记复活（那是绕过 resurrect 的双人隔离）→ 拒

产生时刻取自文件名里的 `_YYYYMMDDTHHMMSSZ`（用 `timegm` 按 UTC 解析），
不用 mtime：`cp` / `checkout` 会把 mtime 刷成"刚刚"，那样任何证据都永远新鲜，
保留期永远不触发。

## §10.25.6 两件没做的事（写在这里，不用"接了三件套"糊过去）

**一、`remote.py` 没有接入。** 本仓库没有任何远端**写**操作；
`verify_executor_pin.py` 的 `gh api` 是幂等 GET。把 `RemoteGateway` 套在一个
GET 上只是装饰——它解决的问题（"目标系统不支持幂等、且查询不可用"）在这里
不存在。它保持 `tested`，不是 `operational`。

**二、控制目录里没有专属控制条目。** 本轮发现：保留期 / 来源识别 / 恢复 /
删除后再现 / 证据生命周期这几件事，在 `control-catalog`（49 条）里**没有
对应控制**。最接近的是 EVD-01（链完整性）、EVD-02（审计不可用失败关闭）、
ISO-01（Run 绑定），都不是同一件事。

同时发现编号口径错误：此前这些模块自称 `ALC-01` / `DG-01` / `REM-01` /
`REM-02`，而这四个编号在 `rule-registry`（53 条）与 `control-catalog`（49 条）
里**都不存在**。它们被写进了 commit message、`audit_policy.json` 的
`control` 字段、`evidence_ledger.json` 的 `control` 字段、以及 CI 步骤名
`T-ALC-01`——看起来像控制编号，实际查不到。现已改为断言编号
（`assertion: AUD-014-03` / `AUD-016-03`）+ `supporting_controls`。

**这是待补的缺口，不是已完成的覆盖**：目前这两条断言只由 §四 断言层承载，
控制层为空。补法有两条路，需要决策而不是顺手写：

- 若规范正文有对应强制条款 → 在 rule-registry 加规则、catalog 加控制、
  双向一致性由 `validate_controls.py` 强制；
- 若规范没有对应条款 → 明确登记为"仅断言层覆盖"，并让 §四 的
  `closure_criteria` 承认这一点（当前 closure 不要求控制级承载即可进评审）。

**附带缺口**：没有任何机器判定检查"代码/提交里提到的控制编号是否真实存在"。
`validate_controls.py` 只校验注册表与控制目录之间的双向一致性，不扫引用方。
建议补一个 `check_control_refs.py`（扫描 `governance/*.json`、`scripts/*.py`、
`executor/*.py` 里的 `[A-Z]{2,5}-\d{2}` 形状的 token，凡不是注册规则/控制
且不在显式白名单里即红）。本轮**未实现**。

## §10.25.7 验证

| 项 | 结果 |
|---|---|
| 新增接入用例 | T-GOV-01..20，共 20 条 |
| 全套件 | 223 条全绿（下限 210 → 230，删除余量 0） |
| 变异检验 | 13/13 捕获，每条精确归因 1 条用例，0 逃逸 |
| CI 实跑 | `12 条事件、12 项必需检查全部落地`（run 41158725081） |

变异检验里有一条起初**逃逸**，值得记下来：把 `verify()` 里"审计流不存在"
这道闸门改成恒假后，后面的链校验仍会因 `audit log missing` 判出同样的
退出码 2，用例只断言退出码，照样绿。把断言从"退出码是几"改成"是哪道闸门
拦的"之后才抓住。→ **断言要钉住诊断，不能只钉住状态码。**

## §10.25.8 诚实边界

- 审计流是本地运行产物（`evidence/audit/` 入 `.gitignore`）。CI 每次从空开始，
  所以"保留期"在 CI 里几乎不会触发；它在本地持续累积的流上才有约束力。
- 哈希链只证明"这条流没被改过"，不证明"写入者是谁"——`AUD-014-04` 仍是 manual。
- 证据台账管不到已经交出去的副本（CI artifact、下游缓存）。
- `--all` 在本地会在 T-VD-01b 停下：本地 Owner 凭证本来就能写控制面（人类
  Owner 横跨两域属预期，见 `verify_credential_domain.py` 的 INFO）。CI 里
  `GITHUB_TOKEN` 是 `contents: read`，才会通过。这不是缺陷，是环境差异，
  但**意味着"本地全链路绿"这件事在本机拿不到**。
